# /specify — 要求仕様の作成

引数(またはユーザーの直前の依頼)を機能要望として受け取り、`docs/specs/NNN-slug/spec.md` を作成する。**このスキルでは実装しない。設計にも踏み込まない**(実装方法は /spec-plan の仕事)。

## 手順

1. **前提を読む**: `docs/vision.md`(柱と非ゴール)、`docs/improvement-policy.md`(現在の優先順位)、`docs/specs/` の既存 spec 一覧(重複・関連の確認)
2. **vision 整合を判定する**:
   - 非ゴール(DAW 化・五線譜浄書・共有プラットフォーム・モバイル編集)に抵触する要望は、実装に進まず抵触点を説明し、vision に沿う代替案を提示する
   - improvement-policy のロードマップ上の位置(順番を飛ばす価値があるか)を一言評価する
3. **番号を採番する**: `docs/specs/` 内の既存 NNN の最大値 + 1(3 桁ゼロ埋め)。slug は英小文字ケバブケース
4. **spec.md を書く**: `docs/specs/templates/spec-template.md` の全セクションを埋める
   - 受け入れ基準は EARS 形式(WHEN/THEN)でテスト可能に書く。Fretpad 特有のエッジケース(カポ、変拍子、連符、タイ、空ドキュメント、休符)から該当するものを必ず含める
   - 要件が曖昧な点は AskUserQuestion で確認する。確認できない場合は「要確認」セクションに仮の判断と共に明記する
5. **レビューエージェントにかける**: Agent ツールで `spec-reviewer` を起動し、指摘を spec に反映する(反映内容を要約して報告)。UI に触れる spec の場合は `ux-designer` も並行して起動し、ペルソナ視点の指摘(空状態・初見時の理解可能性・キーボード操作)を受け入れ基準に反映する
6. **報告する**: 作成した spec のパス、vision との対応、要確認事項を提示し、問題なければ status を approved にして /spec-plan に進むようユーザーに案内する

## してはいけないこと

- 実装方法・ファイル構成・型定義を spec に書く(design.md の領分)
- 非ゴール抵触を黙って通す
- 曖昧な受け入れ基準(「使いやすくする」「高速にする」など観測不能な表現)
