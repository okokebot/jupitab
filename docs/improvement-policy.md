# Fretpad 改善方針 — ペルソナ再確認と次の一手

作成日: 2026-07-03
位置づけ: [vision.md](vision.md) を正としたうえで、Phase 0 完了+記譜拡張(未コミット分)時点での改善の優先方針を定める。[notation-gap-analysis.md](notation-gap-analysis.md) の再解釈を含む。

---

## 1. ペルソナの再確認

vision.md のペルソナは作者自身:

> TAB 譜をなぞって弾くことはできるが、音名・コード名・音楽理論が頭に入らず、アドリブができない。

ここから導かれる、これまで暗黙だった重要な含意を明文化する:

**ペルソナは「記譜の初心者」でもある。** 音楽理論を知らない人は、テヌート・マルカート・プリベンドといった記譜用語も知らない。採譜経験がなければ「付点」「連符」「タイ」の違いも曖昧である。つまり Fretpad にとって記譜語彙は前提知識ではなく学習内容の一部であり、**UI 自体が教材でなければならない**。

### ギャップ分析レポートとの関係(重要な再解釈)

[notation-gap-analysis.md](notation-gap-analysis.md) は「プロの採譜者」ペルソナで書かれており、その指摘の多く(¼ ベンド、途中挿入、コード名、運指、ハーモニクス等)は既に実装された。しかしプロ視点の残項目(複声部、リズムスラッシュ、反復記号の充実など)を追い続けると、**記譜機能の網羅 = Guitar Pro 化**に向かってしまう。これは vision の非ゴールに近づく方向である。

**方針: 記譜語彙の拡張は一旦十分とし、投資先を「学習者が使えること」と「理論レンズ」に切り替える。**

### 現状の症状(ペルソナ視点)

1. **ショートカットが 29 個**(`keymap.ts`)あり、ラベルは「テヌート」「マルカート」「レットリング」等の専門用語のみ。ペルソナはその用語も、対応する記号が譜面上のどれなのかも知らない
2. **白紙から始まる**。コード表はフォームを手で置くしかなく(コード名からの自動生成は vision 柱 1 に明記されているが未実装)、「何を書けばいいか」の足がかりがない
3. **理論レンズが 0%**。`theory.ts` に `degreeInKey` / `scalePitchClasses` / `isInScale` は実装済みだが、UI からは一切参照されていない。最大の差別化点(vision 柱 2)が未着手

## 2. 改善の 3 本柱

### 柱 A: 「UI が先生になる」— 用語と記号を使いながら覚えられる UI

ペルソナは用語を知らない前提で、**操作 ↔ 用語 ↔ 譜面上の記号** の 3 つを常にセットで提示する。

1. **キーマップ表の拡張**(`keymap.ts` は既にヘルプ表示の単一情報源なので土台がある)
   - `KeyBinding` に `description`(1〜2 文の平易な説明: 何の奏法か、どう聞こえるか)と、譜面上でどう見えるかのミニプレビュー(SVG 断片 or 記号文字)を追加
   - 例: 「h ハンマリング — 弾かずに指を叩きつけて音を出す奏法。譜面では音符間の ⌒ と H で表示」
2. **譜面側からの逆引き**: TabSvg 上の記号(スタッカートの点、P.M.、◇ など)にホバー/タップで名称と説明をツールチップ表示。「この記号なんだっけ?」を譜面上で解決できる
3. **音で確認**: 再生機能(`audio/player.ts`、実装中)と接続し、ヘルプの各奏法に「試聴」ボタンを付ける。用語 ↔ 記号 ↔ 音が結びつくのが最も学習効率が高い
4. **段階的開示**: 初期ヘルプは基本操作(入力・移動・音価・小節)だけを上段に、奏法系は「アーティキュレーション」として折りたたむ。29 個を一度に見せない

### 柱 B: 「白紙をなくす」— サンプルとテンプレート

書き始めの摩擦を下げ、かつサンプル自体が教材になるようにする。`samples.ts`(リズムサンプル)のパターンを横展開する。

1. **コードフォーム辞書**: コード表ブロックで「コード名を選ぶ → 代表的な押さえ方が自動生成 → 手動編集」(vision 柱 1 の未実装分)。まずオープンコード + 基本バレーコード(E/A フォーム)の静的辞書で十分。ルート・3rd・5th を度数付きで色分けすれば柱 C とも連動する
2. **コード進行テンプレート**: 「12 小節ブルース(E)」「2-5-1(C)」「カノン進行」等を、コードシンボル入りの TAB ブロック+解説テキストブロックのセットとして挿入できる。コードシンボル(`c` キー)は実装済みなので土台がある
3. **スケールサンプル**: 「A マイナーペンタ ボックス 1」等の指板図+運指 TAB のセット。柱 C の自動マーキングができればテンプレートはほぼ生成できる

### 柱 C: 「度数の自動計算」— 理論レンズの実装(Phase 1 本丸)

ユーザー要望「ルートやスケールから度数が自動計算される機能」は、vision Phase 1 の理論レンズそのものである。モデル関数は実装済みなので、UI を作れば動く。

1. **指板図の自動マーキング**: ブロックにルート+スケールを設定すると `scalePitchClasses` で構成音を自動マーキングし、各マーカーに `degreeInKey` の度数(R, ♭3, 5…)を自動表示。現状の「1 個ずつクリック」は自由注釈用として残す
2. **TAB の音名・度数オーバーレイ**: `keyContext`(型は定義済み)の設定 UI と、表示切替(フレット番号のみ / +音名 / +度数)。スケール外の音は消さず弱く表示(ギャップ分析 §4-5 のとおり)
3. **理論の正しさを担保する**(学習アプリなので妥協不可。ギャップ分析 §4 に従う):
   - 異名同音の綴りをキーから導出(A ハーモニックマイナーの導音は G#、A♭ ではない)
   - 度数ラベルの綴り分け(リディアンの #4 を ♭5 と表示しない)
   - `ScaleType` に phrygian / lydian / locrian を追加してモードを網羅

## 3. 優先順位とロードマップ

vision のフェーズ構成は維持しつつ、順序と中身を次のように具体化する:

| 順 | 内容 | 対応する柱 | 規模感 |
|---|---|---|---|
| 1 | 指板図のルート+スケール自動マーキング+度数表示 | C-1 | 小(モデル関数実装済み) |
| 2 | キーマップの説明文+記号プレビュー、ヘルプの段階的開示 | A-1, A-4 | 小〜中 |
| 3 | theory.ts の綴り修正・モード追加 | C-3 | 小(ただしテスト重要) |
| 4 | TAB の keyContext 設定 UI+音名/度数オーバーレイ | C-2 | 中 |
| 5 | コードフォーム辞書(コード名 → ダイアグラム自動生成) | B-1 | 中 |
| 6 | 譜面記号のホバー解説+奏法の試聴 | A-2, A-3 | 中(再生実装後) |
| 7 | コード進行・スケールのテンプレート集 | B-2, B-3 | 中(1,5 の後が効率的) |

1 を最初に置く理由: 実装コストが最小で、ペルソナの「スケールと度数を結びつけたい」という核心的な学習体験に直結し、アプリの差別化点(理論レンズ)を初めて可視化できるため。

### 意図的に後回し・やらないもの

- **プロ採譜向け記譜の残項目**(複声部、リズムスラッシュ、反復記号、カスタムチューニング編集)— 学習者ペルソナの当面の必要を超える。要望が実際に出てから
- **選択・コピー&ペースト**(ギャップ分析 1-2)— 実用上は重要だが「学習体験」より「編集効率」の問題。理論レンズ後に回す
- **チュートリアル動画・ツアー UI** — 作り込みコストが高い。まずヘルプとテンプレートの充実で代替

## 4. 検証方法

作者 = ペルソナなのでドッグフーディングが基本。各施策後に以下を自問する:

- **柱 A**: ヘルプを見ずに(または見ながら 1 回で)目当ての奏法を入力できたか。譜面上の記号の名前を言えるようになったか
- **柱 B**: 新しいノートを白紙から書き始めるのをためらわなくなったか
- **柱 C**: 「このフレーズの 3 音目はキーの何度か」に、アプリを見て即答できるか。数週間後、アプリを見ずに答えられる音が増えたか(= 内在化の進行)
