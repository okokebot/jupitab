# 記譜機能ギャップ分析

調査日: 2026-07-03
調査者: サブエージェント(ペルソナ: ギター演奏に精通するプロの音楽家。音楽理論を熟知し、採譜経験多数)
対象: Phase 0 完了時点(コミット e14d52f)のスコア機能

判断基準: 「Guitar Pro の完全再現」ではなく「採譜メモ・分析ノートとして書きたいものが書けるか」([vision.md](vision.md) 参照)。

---

## 1. 致命的な不足(これがないと採譜・学習ノートとして書けない)

### 1-1. コードシンボル(小節・拍単位のコード名表記)

**最重要。** `types.ts` の `Measure`/`TabEvent` にコード名を置く場所が一切なく、TAB の上に「Dm7 | G7 | Cmaj7」を書けない。

- **ユースケース**: ジャズのソロやコンピングを採譜するとき、フレーズは必ず「その瞬間に鳴っているコード」とセットで記録する。「この音は G7 の ♭9」という分析こそが本アプリのコンセプトそのものなのに、進行を書く場所がない。ブルース 12 小節の把握も同様。
- さらに vision.md の Phase 3「コードトーン/テンションの色分け」は、コード進行データがモデルに存在しないと成立しない。**理論レンズの土台として Phase 1 前にモデルへ入れるべき**(キーは KeyContext で持てるが、コードは持てない)。

### 1-2. 選択・コピー&ペースト(イベント/小節単位)

`tabOps.ts` に範囲選択・複製の概念がない。カーソルは単一位置のみ。

- **ユースケース**: 採譜は「同じリフが 4 回、3 回目だけ最後が違う」の連続。ロックのリフ採譜で 1 小節を 8 回打ち直すのは実用に耐えない。学習ノートでも「同じフレーズを別ポジションで書き比べる」のに複製は必須。

### 1-3. クォーターチョーキング(¼ ベンド)

`Bend.semitones` が整数(1=半音, 2=全音)で、**ブルースで最頻出の ¼ ベンド(ブルー・ノートのしゃくり)が表現できない**。

- **ユースケース**: B.B. King や SRV のフレーズを採譜すると、3rd に対する ¼ カールが 1 コーラスに何度も出る。これが書けないと「ブルースの採譜メモ」が成立しない。TabSvg の `bendLabel` も 1 半音未満を想定していない。

### 1-4. 前打音(グレースノート)

モデルに装飾音の概念がない。

- **ユースケース**: ロック/ブルースの「下からのクイック・スライド」「装飾ハンマリング」は事実上すべてのソロに出る。現状は 32 分音符などで代用するしかなく、小節の音価計算が崩れる(overfull 警告が出る)か、リズムの実態と乖離した譜面になる。

### 1-5. イベントの途中挿入

`insertEventAfter` は tabOps に**実装済みだが、キーバインドがない**(Space は末尾追加のみ、`keymap.ts` に挿入キーなし)。

- **ユースケース**: 採譜は「聞き直したら音が 1 個多かった」の繰り返し。小節の途中に音を挿入できないと、以降を全部打ち直すことになる。編集操作としては致命的。

### 1-6. どこからでもないスライド(slide in / slide out)

`legatoToNext` は「次の音への接続」しか表せず、不定音程からのスライドイン(`/5`)・スライドアウト(`5\`)が書けない。

- **ユースケース**: フレーズの入り・終わりのスライドはロック・ブルース採譜の基本語彙。「次の音がある」前提のモデルでは書き漏らしが構造的に発生する。

## 2. あると大きく価値が上がるもの(優先度順)

1. **イベント/音符への自由注釈(テキストメモ)** — 「ここは CAGED の C フォーム」「ミクソリディアンに切替」を音の真上に書けること。ブロック単位の `label` しかない現状では、"分析ノート" というコンセプトに対して注釈の解像度が粗すぎる。理論レンズと並ぶ差別化点になりうる。
2. **反復記号・セクション構造** — リピートバーライン、1・2 番カッコ、セクションラベル(A/B, Verse/Chorus)。12 小節ブルースや AABA の「構造の理解」自体が学習内容。テキストブロック分割で代替は可能だが、譜面内に書けると採譜メモの完成度が段違い。
3. **リズムスラッシュ(コード弾き用の斜線譜)+ ストローク方向(↓↑)** — コンピング・カッティングの学習は「押さえ方 + リズム + ストローク」で成立する。6 弦全部にフレット番号を書くのは冗長で、実務ではスラッシュ+コード名で書く。
4. **タッピング(T)・ピッキング指示(ピック/指、i-m 交互など)** — 奏法メモとして頻用。`Articulation` の追加で済む軽いもの。
5. **複声部(2 ボイス)** — ジャズのコードメロディやトラヴィス・ピッキングは「ベース声部 + メロディ声部」が別リズムで動く。現状の `TabEvent` 単声モデルでは原理的に書けない。ただしコストが大きいので、当面は letRing + 和音で近似し「割り切り」を明記する判断もあり。
6. **カスタムチューニング編集・弦数変更** — モデルとレイアウトは弦数可変(`tuning.length`)に対応済みなのに、UI はプリセット 4 種のみ(`TabBlockView.tsx` の `TUNINGS`、「カスタム」は disabled)。オープン G などの学習ノートが書けない。
7. **スウィング/シャッフル指定** — 「♪♪=3連」の一言。ラベル欄で代用可能なので優先度は下げてよいが、再生(Phase 2)では必須になる。

## 3. データモデル/演算は対応済みだが、描画・編集 UI が欠けているもの

コードを読んで確認した具体的な乖離:

| 要素 | モデル/演算 | 欠けているもの |
|---|---|---|
| `TabNote.finger`(運指) | types.ts にあり | **描画も編集 UI も皆無**(TabSvg は参照せず、keymap にもない)。ChordBlock には指セレクタがあるのに TAB にはない |
| `TabNote.harmonic` | types.ts にあり、TabSvg は `◇5` を描画 | **入力手段ゼロ**(tabOps に toggle なし、keymap になし)。また natural / artificial の描画区別なし(A.H. 表記なし) |
| `tenuto` / `marcato` | `toggleArticulation` で操作可、TabSvg の `ANNOTATIONS` に描画あり | **キーバインドなし**(TabBlockView の handleKeyDown に分岐がない) |
| `Bend.kind`(bendRelease / prebend) | 型定義あり | `cycleBend` は `'bend'` 固定、描画も kind を無視して常に上矢印。**チョーキング・リリース/プリベンドが入力も描画もできない**。1 音半以上のベンドも入力不可(`bendLabel` は表示対応済み) |
| 任意連符(5 連・6 連など) | `tuplet: {actual, normal}` は任意比、`tupletGroups`(tabLayout.ts)も汎用対応 | UI は `t` キーの 3 連トグルのみ |
| 部分バレー・複数バレー | `Barre{fromString,toString}` + 描画は対応済み | ChordBlockView の編集 UI は「6→1 弦の全弦バレー 1 本」のみ。**A 型バレー(5〜1 弦)すら作れない** |
| `keyContext` | TabBlock / FretboardBlock 両方にあり | UI・オーバーレイ未実装(Phase 1 予定どおりだが、ChordBlock には keyContext 自体がない点に注意) |
| `tempo` | TabBlock にあり | UI なし(Phase 2 でよい) |
| `insertEventAfter` | tabOps に実装済み | キーバインドなし(前掲 1-5) |

描画バグ気味の点: TabSvg のスライド線は `y+3 → y-3` 固定で**常に上昇向き**。下降スライド(7→5)でも上向きの線になる。フレット比較で向きを変えるべき。

## 4. 理論レンズ(Phase 1)への示唆 — 音楽教育の観点

現状の `theory.ts` はピッチクラス(0–11)ベースで、Phase 1 の要件に対して以下の構造的な限界がある:

1. **異名同音の綴りはキーから導出すべき**。現在は `preferFlats` の手動フラグ + 固定テーブルだが、正しい綴りは「キーの音度」で決まる。例: A ハーモニックマイナーの導音は **G#** であり A♭ ではない(FLAT_NAMES では A♭ になる)。F# メジャーなら A# であり B♭ ではない。学習アプリで綴りが間違っていると**誤った理論が内在化される**ので、ここは妥協できない。`preferFlats` は「デフォルトをキーから自動決定 + 手動オーバーライド」に。
2. **度数ラベルもスケール文脈で綴り分けが必要**。`DEGREE_NAMES` は ♭ 系固定なので、リディアンの #4 が「♭5」と表示される。ブルーススケールの ♭5 とリディアンの #4 は同じ半音距離でも教育的意味が真逆。スケール定義側に「各音度の綴り」を持たせるべき。
3. **モードの網羅**: `ScaleType` に phrygian / lydian / locrian がなく「モード対応」として不完全。ジャズ学習ペルソナなら altered・lydian dominant(メロディックマイナー系モード)も将来欲しくなる。なお `melodicMinor` は上行形のみの定義で、これはジャズ的用法(ジャズマイナー)としては正しい — その旨をどこかで明示するとよい。
4. **キー基準とコード基準の 2 つの度数は別物**。C メジャーキーの Dm7 上の F 音は「キーの 4」だが「コードの ♭3」。アドリブ学習で本当に効くのは後者(コードトーン/テンション: R, 3, 5, 7, 9, 11, 13)。テンションは 2/4/6 でなく 9/11/13 と表記するのが慣例。→ 前掲 1-1 のコードシンボルがモデルに必要な理由。
5. **スケール外の音の扱い**: `degreeInKey` が常にクロマチックなラベルを返し、`isInScale` で内外判定できる現設計は正しい方向。経過音・アプローチノートを「表示しない」のではなく「スケール外として弱く表示」するのが学習的に正しい。
6. **カポと表示音高**: `pitchFromTab` はカポ込みの実音を返す。カポ 2 で Am フォームを弾くと Bm が鳴る — 「フォーム上の音名」と「実音」のどちらを見せるか(または両方か)を理論レンズの仕様として明示的に決める必要がある。学習目的なら実音がデフォルトであるべきだが、混乱ポイントなので UI 上の説明が要る。
7. **タイで結ばれた音**: 度数・音名オーバーレイはタイの 2 音目に重複表示しない、が浄書慣例。

## 5. 非ゴールとして切って良いもの(プロ視点でも学習ノートには不要)

- **五線譜の浄書全般** — TAB + 符幹リズム表記で学習ノートは十分成立する。現在の「譜の下にリズム記号」方式は実用譜(Guitar Pro の TAB 単独表示や教則本)と同じで正しい割り切り。
- **複声部の完全な浄書**(声部別の符幹方向・声部間衝突回避)— 2 ボイス自体は価値があるが、その「美しい浄書」は不要。
- **Guitar Pro 式のベンドカーブエディタ**(時間軸上のベンドポイント編集)— ラベル(½/full/release)ベースで学習ノートには十分。
- **強弱記号体系**(pp〜ff、クレッシェンド松葉)— ギターの学習メモではアクセント/ゴーストで実用上足りる。
- **D.S. / Coda 等の複雑な反復ネスト** — リピートバー + セクションラベルまでで十分。それ以上はテキストで書けばよい。
- **ネスト連符・64 分以下の細分・フェルマータ等の高度な記譜** — 採譜メモで使う場面がほぼない。
- **歌詞、マルチトラック(ベース/ドラム)、MusicXML/GP 完全互換** — vision.md の非ゴールと整合。切ってよい。
- **再生のグルーヴ再現**(スウィングの揺れ、ベンドの音程カーブ)— Phase 2 の再生は「音高とリズムの確認」ができれば学習目的は達成される。

## 総括

音価・連符・タイ・変拍子まわり(fraction ベースの厳密計算、6/8・7/8 対応、overfull 警告)は学習ノートとして既に堅牢で、単音フレーズの採譜は今でも書ける水準。一方で以下の 3 点が「採譜メモとして実戦投入」を阻んでいる:

- **(a) ハーモニーの文脈(コードシンボル)を書く場所がない** — Phase 1 理論レンズの前提でもあるため、モデル設計の先行を強く推奨
- **(b) ブルース系の語彙の欠落** — ¼ ベンド・グレースノート・スライドイン/アウト
- **(c) 反復編集の不在** — コピー&ペースト・途中挿入
